# Formal Verify Orrery

Exhaustive finite-state model checking for Orrery's highest-stakes concurrency, lifecycle, and access-boundary invariants. The checker extracts the active locks and transition guards directly from Orrery's server source and SQL migrations, then runs a breadth-first search (BFS) over all reachable concurrent interleavings to verify safety and liveness properties.

## Run the Check

One command, zero external dependencies (requires only Python 3.10+, runs in `< 0.3s`):

```bash
python3 .agents/skills/formal-verify-orrery/scripts/verify.py
```

For machine-readable output (extracted code facts + counterexample traces):

```bash
python3 .agents/skills/formal-verify-orrery/scripts/verify.py --json
```

Exit code `0` means every property passed; exit code `1` means at least one property failed and its shortest counterexample trace was printed in Orrery's own function names.

## Tool Choice

We use a **zero-dependency Python 3 exhaustive BFS model checker** paired with source-guard extraction rather than TLA+/TLC or Quint because:
1. Neither a JVM/TLC nor Quint is installed on the dev environment or CI by default, while `python3` is always available.
2. Source-guard extraction binds the model directly to the live TypeScript and SQL files, so removing a lock or guard (e.g., dropping `.for("update")` or `lockWorkspaceForMutation`) immediately switches the model to the unguarded transition relation and produces the real counterexample trace.
3. If you author a new TLA+ specification for a future subsystem (e.g., #27 project permissions or #38 account deactivation), read its output with `/statechart`.

## What Is Not Covered

- **SQL/Drizzle runtime semantics & deadlocks across unrelated tables**: The model checks the extracted design and lock ordering, not PostgreSQL's query planner or migration SQL syntax. Always pair this skill with `pnpm test` (real Postgres via Testcontainers) and `/verify-orrery` for end-to-end runtime proof.
- **UI & HTTP transport**: Cookie flags, Zod validation, and React state are outside this model; cover them with `pnpm check`, `pnpm test`, and `/verify-orrery`.
- **M36 storage and transaction boundaries**: M36 is a bounded design model driven by source markers. It interleaves reserve/put/clock/activate with sweep claim/blob-delete/row-delete and a failing backend, but it does not replay a real Postgres `UPDATE ... RETURNING` row lock, a real object store, or the 60s timer. The sweep now lives in `platform/object-sweep.ts` and is shared with attachments. The real-Postgres `avatars/avatars.test.ts` proves both race paths (activation before and after `store.delete`), activation after the sweep removed the row, the clean 409 `avatar_upload_expired` Problem, the accurate `reclaimed` count on a failed backend delete, and that an old `active` row is never claimed. `check_m36` itself flips each of its 5 source guards and requires a named counterexample.
- **Unbounded actor counts**: M1 is bounded to 3 humans / 2 concurrent writers; M4 is bounded to 3 concurrent `PATCH`es.
- **M9 transaction boundary**: M9 is a bounded design model driven by source markers. It assumes atomic transitions; it cannot prove that token, account, membership, and grant writes use the same transaction or roll back together. The real-Postgres workspaces tests check both successful acceptance paths, verify database state after a stale-scope rejection, and prove that an owner's stale-scope offer is superseded by a fresh invitation that a recipient can accept.
- **Project transfer (#46)**: M9 models a project moving out of the invited workspace before redemption, but not the transfer operation itself. Use the scoped invitation recipe in `verify-orrery/features/workspaces.md` for REST and browser checks.
- **M10 transaction boundary and concurrency**: M10 enumerates independent authority decisions in a bounded design model; it does not explore interleavings between two capability changes and a redemption, and it assumes the rejected `inviter_not_authorized` path rolls back the token and every earlier write in the transaction. Real-Postgres tests in `workspaces.test.ts` assert the invitation stays pending and no membership, account, or project grant commits. The live REST recipe in `verify-orrery/features/workspaces.md` covers the same ceilings through HTTP.
- **M11 transaction boundary and revocation races**: M11 enumerates independent key decisions in a bounded design model; it does not replay a real interleaving of an authentication transaction with a revocation or project-grant change, and it assumes the rejected paths write no key or event. The real-Postgres `agents.test.ts` proves the just-before/just-after expiry boundary in database time, the issuance ceiling, the lowered/removed grant ceiling, idempotent revocation, owner-revocation isolation, the audit rows, and that the database trigger rejects a cross-workspace key grant. The real-Postgres `workspaces.test.ts` proves that `removeMember` revokes the member's keys with one secret-free event, that re-invitation cannot revive the old credential while a new key works, and that `issueKey` and `removeMember` queue on the same ownership lock with no unrevoked key surviving. The black-box `zz-agents.spec.ts` proves the same HTTP outcomes against the running image, including human self-revocation.
- **M12 transport and attribution boundaries**: M12 is a bounded design model driven by source markers. It checks that the tool set and the two adapters call the one service gate and that the actor columns/constraints exist; it does not replay MCP frames or prove a particular HTTP status. The real-Postgres `agents.test.ts` proves agent attribution in stored rows and activity, Read-vs-Contribute denials, dynamic human-access capping, workspace/project scoping, and REST denial parity. The black-box `zz-mcp.spec.ts` drives the actual MCP protocol client against the built image for the same flows, including tool-list exposure, cross-workspace `list_projects`, out-of-scope, and revoked keys.
- **M13 query shape and payload contents**: M13 is a bounded design model driven by source markers in the history service, its thin REST adapter, and the shared contract. It checks which decisions exist and which fields a projection may select; it does not execute a SELECT or serialize a real response. The real-Postgres `history.test.ts` proves the scope matrix, non-enumeration status codes, all recorded event kinds through the view, and secret-free bodies. ## Interpreting Failures & Maintaining the Skill

- **Real bug vs. modeling error:** Open the files listed in the failing check's output. If a lock, guard, or SQL predicate was removed or reordered, the counterexample trace shows a real bug — fix the product code and add a real-Postgres regression test. If the product code was intentionally refactored to enforce the same invariant via a *different* mechanism (e.g., a new DB constraint or different helper name) so `extract_code_facts()` no longer recognizes it, update `extract_code_facts()` and the transition model in `scripts/verify.py` to match the new mechanism, prove it still fails when the mechanism is broken, and advance the sync commit above.
- **Sensitivity proof:** each `attempts` tuple carries the outcome *when its guard is missing*, so a deleted source guard makes the shortest counterexample name the exact request. To prove a model is sensitive without editing product code, import `scripts/verify.py`, copy `extract_code_facts()`, flip one fact to `False`, and assert the check becomes `violated`; restore by rerunning the normal command. M13 was proven sensitive to `m13_workspace_404`, `m13_admin_only`, `m13_no_secret`, `m13_session_only`, and `m13_manage_access` when it was added. M16 was proven sensitive to all 13 of its extracted guards (lock, source ownership, revoked/expired/workspace refusals, same target, one-time secret, independent expiry, grant capping, non-cascading lineage FK, secret-free event, history surface, and 400 Problem) plus the shared password-reset guard.
