# Runner harness catalog, on-demand ACP probing, and per-dispatch execution options

Extending manual delegation (#236) with a custom dispatch prompt and per-dispatch `harness`, `model`, and reasoning `effort` selection builds directly on [ADR-0010](0010-local-agent-runner-and-live-streaming.md) while introducing three lasting protocol and security commitments across the server, contract, and `orrery-runner`.

Each live **Runner** owns its **Harness catalog** (stored on `runners`, separate from free-form `capabilities` and not host-wide on `runner_hosts`) because project-local configuration (such as `.opencode/`) and per-process CLI overrides (`--acp-command`) can vary across checkouts on the same **Runner host**. `orrery-runner` auto-detects installed ACP-compatible harnesses from a built-in preset registry (shared with #229), includes any explicit `--acp-command` override and optional `~/.config/orrery/harnesses.json` entries, probes their models and default-model reasoning options over ACP (`session/new`), sends the initial catalog on `POST /api/runners/register`, and pushes updates via `PUT /api/runners/{runnerId}/catalog` so five-second heartbeats remain small (`activeSlotCount` only). Because some ACP harnesses only expose reasoning effort options for their currently active model, selecting an unprobed model in the Delegate modal triggers an owner-only `POST /api/runners/{runnerId}/catalog/probe` request (30-second per-model cooldown) that enqueues a short-lived `probe_model` (or `probe_catalog`) command onto the existing `runner_commands` outbox and `pg_notify` doorbell — making `dispatch_id` and `dispatch_attempt_id` nullable under a Postgres `CHECK` constraint that still requires them for `dispatch`, `cancel`, and `input_resolved`. The Runner executes probe commands outside its work slot pool (never blocked by busy slots), serialized by a lightweight per-Harness probe/spawn lock so a concurrent Dispatch for the same Harness never starts while a probe has temporarily switched the Harness's default model (and a Dispatch omitting `model` explicitly passes the Harness's cached `defaultModel`). Each `probe_model` runs a bounded 5-second ACP session that restores the Harness's previous default model and options before closing — including a short restore attempt (or one-shot recovery restore if killed mid-probe) on timeout/failure so the user's local CLI default is never left mutated. Both `orrery-runner` (serializing `PUT /catalog` writes) and the server preserve previously `"known"` per-model effort entries across startup and manual catalog refreshes so a slower refresh can never overwrite discovered effort levels back to `"unknown"`.

A **Dispatch** may carry optional `prompt` (bounded to 16,000 characters, visible to all project readers, appended after the Runner's operational worktree/MCP preamble), `harness`, `model`, and `effort`; `acceptDispatch` records the chosen `harness` and `model` onto the resulting **Run**. The server never sends executable paths or CLI flags: `orrery-runner` resolves `harness` strictly through its local registry/config allowlist, failing fast with a typed diagnostic and releasing the session if the requested `harness` is unavailable or the harness rejects the requested `model`, while treating an unsupported `effort` as non-fatal (omitting effort and emitting a warning chunk). Piggybacking the full catalog on every heartbeat was rejected to avoid repeated write amplification on `runners`; adding a separate WebSocket or inbound probe port was rejected for the same OpenAPI-first, NAT-friendly, and Go/Rust-portability reasons established in ADR-0010.
