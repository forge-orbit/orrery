# Human-only issue assignees, owner-delegated claims, and label-routed auto-claim

Separating **accountability** from **execution** resolves two recurring UX and authorization flaws in polymorphic `(assignee_type, assignee_id)` issue assignment (issue #276): humans could not delegate their own assigned issues to a local **Runner** without unassigning themselves, and assignee pickers mixed accountable team members with every registered **Agent** even though **Work session**s, **Run**s, and **Dispatch**es already track active agent execution. This supersedes the polymorphic agent-assignee and strict-claim policy in [agent-board-interaction.md](../design/agent-board-interaction.md#3-board-assignment-as-a-pull-queue-hint) and amends the `issues.assignee` compatibility clause in [ADR-0010](0010-local-agent-runner-and-live-streaming.md).

An issue's **Assignee** is strictly a single **Human** (or unassigned), enforced in Postgres by collapsing `issues.assignee_type` and `issues.assignee_id` into a single nullable `assignee_human_id` foreign key referencing `humans(id)` (indexed on `assignee_human_id`). The migration backfills existing `assignee_type = 'agent'` rows to `agents.human_id` (the agent's owner human, falling back to `NULL` only if no agent row exists) and preserves historical `project_activity.changes` JSONB entries so legacy agent-assignee diffs remain readable. On REST and MCP contracts, `create_issue` and `update_issue` accept `assigneeHumanId: Uuid | null`, `Issue.assignee` returns `{ humanId, displayName } | null`, and the two legacy `409` claim codes (`issue_assigned_to_human`, `issue_assigned_to_other_agent`) collapse into a single `issue_assigned_to_other_human` code.

Claim and dispatch eligibility follow one uniform invariant across direct MCP/REST `claim_issue`, `reacquire`, `Delegate to Runner`, `orrery-runner work`, and `orrery-runner start --auto-claim`: an **Agent** may claim or be dispatched an issue if and only if the issue is unassigned OR assigned to that agent's owner **Human** (`issue.assigneeHumanId === null || issue.assigneeHumanId === identity.humanId`). Assigning an issue to a human never mutates on dispatch, and another human's agents are always rejected (`409 issue_assigned_to_other_human` / `issue_not_claimable`). Reassigning an already `in_progress` issue to another human via `update_issue` remains permitted without auto-stopping the active **Work session** (a human can still explicitly request Stop); the owner-match guard is enforced at claim, dispatch, `acceptDispatch`, and `reacquire` boundaries, so a mid-flight reassignment blocks any subsequent `reacquire` or queued dispatch acceptance by the previous owner's agents.

Autonomous queue routing replaces agent-assignee matching with owner-human scoping plus project **Label** filtering. `ready_work` (REST/MCP) and `autoClaim` (REST) redefine `assignedToMe` for agents and **Runner**s to match issues assigned to the agent/runner host's owner **Human** (sorting owner-assigned issues before unassigned), and accept an optional `labels?: string[]` filter (AND semantics, case-insensitive label name match). In `orrery-runner start --auto-claim`, `--auto-claim-filter` continues to default to `assignedToMe`, and `--auto-claim-label` defaults to `ready-for-agent` (repeatable for multi-runner specialization, with `--auto-claim-any-label` to opt out) so autonomous daemons never silently pull personal human `todo` issues. Interactive MCP `ready_work` keeps `labels` optional so an agent explicitly invoked by its owner human can still inspect and claim any of that human's `todo` issues.

Splitting this into a two-step rollout (temporarily relaxing human-assignee checks while keeping polymorphic agent assignees) was rejected because it would duplicate changes across claim guards, runner dispatch, and formal verification models (`verify.py`) while leaving ambiguous `assignedToMe` semantics and noisy UI pickers in place. Adding a dedicated `agent_ready` boolean column on `issues` was rejected in favor of existing project-scoped **Label**s, which handle both opt-in gating (`ready-for-agent`) and multi-runner specialization (`frontend`, `backend`) without schema rigidity.
