# Local agent runner: host/runner identity, transactional HTTP/SSE transport, ACP supervision, and ObjectStore stream rollup

Delegating issues to local coding agents behind NAT/Wi-Fi (issue #162) introduces lasting commitments across authentication, transport, execution ownership, local safety, and live stream storage. Orrery already models `Agent`s, `Run`s, 5-minute DB-leased `Work session`s, `work_session_activities`, `questions`, and portable `ObjectStore` blobs ([ADR-0008](0008-pluggable-object-storage.md)); the local runner must extend that model without duplicating execution state, breaking OpenAPI-first portability, or adding external brokers (Redis/RabbitMQ) to Orrery's single-database deployment.

Identity is split into two levels plus ephemeral execution credentials: a `Runner host` (`runner_hosts`) is an installation-wide enrolled machine owned by one `Human` via browser device-code login (`orrery-runner login`, bound with a verifier secret, storing a `0600` host credential on disk) and revocable as a unit; a `Runner` (`runners`) is a live `orrery-runner` process bound to one workspace, project, default `Agent` (overridable on manual dispatch when compatible with `issues.assignee`), and opaque `repoFingerprint` (raw local paths are never stored on the server). Presence (`Online` / `Busy` / `Offline`) is derived in DB time from `last_seen_at` and live work sessions, never stored as a mutable boolean. Dispatch authorization is strictly `owner_only` by default (`runner_hosts.human_id === actor.humanId`), while emergency `requestStop` remains available to any project contributor/manager. When a `Runner` accepts a `Dispatch` (`runner_dispatches`), the server atomically creates/joins the `Run` (using `dispatchAttemptId` as initial `nativeSessionId`), claims the `Work session` via Orrery's existing services, and mints a short-lived `Dispatch token` (`orr_dt_...`) scoped strictly to `(runnerHostId, runnerId, dispatchId, dispatchAttemptId, agentId, workspaceId, projectId, issueId, runId, workSessionId)` for `/mcp` and session telemetry. `AgentAuthenticator` and `agentProjectAccessInTransaction` resolve both `orr_ak_...` (`API key`s) and `orr_dt_...` (`Dispatch token`s), enforcing a single-issue tool allowlist and live-checking `work_sessions.status = 'active'`, `work_sessions.lease_expires_at > statement_timestamp()`, active dispatch attempt, `runner_hosts.revoked_at IS NULL`, `runners.revoked_at IS NULL`, `humans.deactivated_at IS NULL`, and live workspace/project access ceilings — so no long-lived workspace `API key` sits on a laptop. Human deactivation revokes installation-wide `runner_hosts`, while workspace member removal revokes only that member's workspace-bound `runners`; both enqueue `cancel` commands for active dispatches, and runners immediately terminate local ACP slots on `401` or `cancel`.

Server-to-runner control uses a Postgres transactional command outbox (`runner_commands`: `dispatch`, `cancel`, `input_resolved`, carrying `commandId`, `dispatchAttemptId`, and `expiresAt`) paired with outbound HTTP SSE/long-poll (`?afterSeq=N`) and a dedicated `pg_notify` listener connection per replica carrying only IDs as a latency doorbell (never a correctness dependency; reconnects always query Postgres first and fall back to slow polling). Runner-to-server streaming spools structured ACP events (tool calls, unified file diffs, plans, child workers), typed diagnostics (`acp_not_installed`, `acp_spawn_failed`, `acp_crashed`, `auth_expired`, `usage_limit`, `provider_overload`, `permission_denied`, `runner_disconnected`), and `owner_only`-tagged raw output chunks to a local JSONL file outside the git worktree (`<repo>/.orrery/runs/<dispatchAttemptId>/stream.jsonl`), then flushes idempotent batched HTTP `POST` (`fromSeq..toSeq`) returning `{ ackedSeq }` or native `429 Retry-After` backpressure. While a session is `active`, chunks sit in an ephemeral hot chunk table (`work_session_stream_chunks`, keyed by `(work_session_id, seq)`) served to the **Live Session Studio** via cursor-based TanStack Query (`?afterSeq=N`), with the server filtering out `owner_only` raw chunks whenever `viewer.humanId !== runner_hosts.human_id`. At session end (or lease-expiry sweep), under a `FOR UPDATE` lock on `work_sessions`, non-empty chunks roll up into a single JSONL blob in `ObjectStore` (`stored_objects`, committed alongside `work_sessions.stream_object_id` and then activated), and hot chunks are pruned — keeping `work_session_activities` as the durable curated timeline while enabling offline replay after laptop sleep.

Locally, `orrery-runner` supervises agents over **ACP (Agent Client Protocol) on stdio** (OpenCode first, any ACP-compatible harness via the same adapter) inside an isolated `git worktree` per slot (default `--concurrency 1`, plus one-shot `orrery-runner work <ISSUE>`). The runner owns the reliability envelope (lease renewal, cancel/crash `stop_session("released")`, and coalesced milestones), while the ACP agent owns domain artifacts over `/mcp` (`claim_issue`, `renew_claim`, and cross-issue mutations are rejected for `Dispatch token`s). The runner enforces a strictly local, worktree-scoped policy on ACP `session/request_permission` (no remote shell-approval button in v1), never auto-deletes dirty/unpushed worktrees on crash or stop, never auto-reruns an uncertain disconnected dispatch on reconnect, and auto-resumes parked ACP sessions on `input_resolved` (triggered by human answer or `fallback_used` deadline sweep) only while the session claim and `Dispatch token` remain active (if a `require_human` deadline expires and releases the claim, an outbox command notifies the runner and resuming requires explicit human re-dispatch).

A persistent bidirectional WebSocket was rejected because WebSocket upgrades sit outside `@hono/zod-openapi` (`contract/openapi.json`), require sticky routing or an external pub/sub bus across replicas, and complicate immediate per-request host/key revocation; HTTP/SSE + transactional Postgres outbox stays 100% OpenAPI-native, proxy-proof, and portable to Go/Rust. Reusing a shared long-lived workspace `API key` across multiple runners was rejected because revoking one runner would only be a soft disconnect rather than a true security revocation and would leave workspace-wide credentials on developer laptops. Persisting raw token/stdout streams directly into `work_session_activities` was rejected to avoid Postgres write amplification and keep the activity timeline semantic.
