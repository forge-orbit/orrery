# External HTTP plugins with two-tier trust and short-lived token exchange

Issue #14 proposed a post-MVP plugin system based on host-managed `go-plugin` gRPC binaries, written when the server was assumed to be Go and before Orrery shipped its service layer and workspace-scoped outgoing webhooks ([ADR-0007](0007-outgoing-webhooks-outbox-and-security.md)). Running third-party binaries inside Orrery's single Docker container clashes with self-hosted operations (OS/architecture mismatches, container rebuild persistence, and process isolation around `DATABASE_URL` and `ORRERY_ENCRYPTION_KEY`) while the primary extension drivers — two-way integrations like GitHub/Slack and future UI panels (#15 Level 4) — are naturally external services.

Orrery models extensions as external HTTP **Plugins** (sidecar containers or remote HTTPS services) speaking language-neutral contracts over versioned REST and signed webhooks, preserving Go/Rust rewrite portability. Authority follows a strict two-tier trust boundary that upholds Orrery's privacy invariant between **System administrators** and **Workspace owners**: a **System administrator** registers a **Plugin** on the **Installation** from a manifest URL or JSON upload (with explicit permission preview and default-deny HTTPS/SSRF enforcement, and no central marketplace or mandatory signing CA in v1), and a **Workspace owner** (or **Personal workspace** owner) explicitly creates a **Plugin grant** approving its capability scopes (`issues:read`, `issues:write`, `comments:write`, `links:write`, `knowledge:read`, `knowledge:write`, `activity:read`) and project scope (`all_projects` plus an explicit project join table, matching [ADR-0007](0007-outgoing-webhooks-outbox-and-security.md) so project transfers never widen access). Plugins never mutate workspace membership, member permissions, or installation settings. Pre-auth login providers (SSO/OIDC, LDAP) are explicitly excluded from the plugin system and remain first-party **Installation** auth adapters like object storage ([ADR-0008](0008-pluggable-object-storage.md)).

Each **Plugin** acts under a dedicated third actor kind in `project_activity`, distinct from **Human** and human-owned **Agent** identities so automated integration history stays clear and independent of member departure. Registration issues a plugin-level `client_id` and `client_secret`, which the **Plugin** exchanges for a short-lived **Plugin token** scoped to one active **Plugin grant** and verified live against that grant's status, capabilities, and project scope on every REST request. Unlike **Agents**, **Plugin** writes do not require an active **Work session** or **Claim**: non-status writes (comments, links, labels) leave live work sessions untouched, while moving an issue out of `in_progress` releases the active **Work session** (`released`), matching **Human** service-layer rules. Outbound events reuse the transactional outbox, backoff retry, timeout, circuit-breaker, SSRF guard, HMAC-SHA256 signing, and metadata-only `version: 1` envelope of [ADR-0007](0007-outgoing-webhooks-outbox-and-security.md) (plugins fetch full content over REST within their granted read scopes), with self-echo suppressed by default so a **Plugin** does not receive events it triggered while other plugins and **Webhooks** still receive them with explicit `actor` metadata. Manifest upgrades that request additional capabilities or events never silently escalate existing **Plugin grants** — grants keep their approved scopes and flag upgrade approval for the **Workspace owner** — and disabling or removing a **Plugin** immediately revokes active **Plugin tokens** and halts deliveries while retaining a tombstone identity so `project_activity` history remains intact ([ADR-0006](0006-soft-delete-and-tombstone-scrubbing.md)). In v1, each **Plugin** stores its own per-workspace configuration and external third-party secrets via an optional external `configureUrl`; sandboxed iframe UI slots (#15 Level 4) are deferred to Phase 2, and plugin-contributed MCP tools are deferred to v2 (opt-in and namespaced) to avoid bloating every agent's `/mcp` tool context.

Host-managed gRPC child processes (`go-plugin`) were rejected due to container packaging fragility, supervisor overhead, and secret-isolation risk inside the server container. In-process WASM modules were rejected for v1 because bidirectional integrations (inbound provider webhooks, OAuth flows, outbound HTTP clients) fit poorly inside pure sandboxes and would duplicate host runtime work across a future Go/Rust rewrite. In-process Node/JS plugins were rejected because they break language-neutral portability and crash isolation. Reusing **Agent** identities or pushed static per-workspace bearer tokens was rejected because **Agents** are tied to a human owner and **Claim** semantics, and pushed static tokens complicate rotation and force stateless sidecars to maintain per-workspace secret databases.
