# Soft-delete issues, knowledge entries, and projects with 30-day in-place tombstone scrubbing

Teams need a safety net against accidental issue deletion, especially on boards shared with autonomous agents. At the same time, Orrery enforces strict database-level audit integrity: `project_activity` requires a non-null `issue_id` foreign key for every `issue_*` event, and project issue numbering (`ORR-42`) must never be reused or broken.

Deleting an issue is a **human-only** operation (`Contribute` or `Manage`; agents cannot delete issues) that sets `deleted_at` rather than removing the row. Soft-deleting an issue that holds an active work session is rejected (`409`) until the session is stopped or released. Soft-deleted issues are excluded from the board, search, `list_ready_work`, and `blocked_by` checks. A Project manager (`Manage`) can restore a soft-deleted issue within 30 days. After 30 days, a background sweep scrubs mutable content in place — clearing the issue body, deleting its comments, links, labels, and dependencies, and setting `purged_at` so it can no longer be restored — while retaining the minimal tombstoned `issues` row.

Hard-deleting rows after 30 days was rejected because it would force either cascading deletes through `project_activity` (destroying audit history) or relaxing the `project_activity_target_matches_type` constraint with `ON DELETE SET NULL`. Retaining a scrubbed tombstone keeps every database invariant, audit reference, and historical issue number intact while still removing user content after the retention window.

Knowledge entries follow the same rules on their own columns: `knowledge_entries.deleted_at`, `deleted_by_human_id`, and `purged_at` with the same CHECK constraints, `knowledge_deleted` / `knowledge_restored` activity events, and one shared purge sweep. Deleting is human-only (`Contribute` or `Manage`), restoring requires `Manage`, deleted entries disappear from `list_knowledge` and `get_knowledge`, and the purge scrubs the title and body in place. Attachment rows stay referenced (and `syncReferences` is skipped) until the purge, when `purgeHolders` releases them so the object-storage sweep can reclaim the blobs. There is no MCP delete tool: agents cannot trash knowledge.

Projects follow the same 30-day Trash and in-place tombstone scrubbing model (#188) on `projects.deleted_at`, `deleted_by_human_id`, and `purged_at` with the same CHECK constraints and shared purge sweep. Deleting and restoring a project are human-only operations restricted to a Workspace owner in a shared workspace (or the sole owner in a personal workspace); agents are rejected (`403`) and no MCP delete tool exists. Moving a project to Trash is rejected (`409`) if any issue in the project has an active work session or non-ended dispatch, revokes pending project transfer authorizations immediately, and hides the project (`404`) from all project, board, issue, knowledge, search, runner, notification, and webhook surfaces while preserving its Project key, access grants, webhook filters, runners, cross-project dependencies, and attachment/stream references so restore within 30 days is lossless (workspace invitation acceptance skips trashed projects, and already-trashed issues or knowledge entries keep their own independent 30-day purge timers). Restoring after 30 days is rejected (`410`) even before the hourly sweep runs. Moving to Trash and restoring record `project_deleted` / `project_restored` in both `project_activity` (feeding webhooks) and `workspace_events` (using the existing `workspace_events` schema). After 30 days, the purge sweep scrubs mutable content in place on `projects`, `issues`, and `knowledge_entries` (backfilling `deleted_at` / `deleted_by_human_id` from the project on un-deleted child rows so their CHECK constraints hold, setting titles to `"[deleted]"` and `purged_at`), deletes non-audit operational rows (`project_access_grants`, `workspace_invitation_grants`, `agent_api_key_projects`, `project_labels`, `project_transfer_authorizations`, `webhook_projects`, `runners`, `notifications`), releases all attachment and session-stream blobs for sweeping, frees the Project key (`one_project_key_per_workspace` scoped to `purged_at IS NULL`), and retains minimal tombstones and audit logs (`project_activity`, `project_access_events`, `workspace_events`).
