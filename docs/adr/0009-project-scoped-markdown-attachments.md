# Project-scoped Markdown attachments with reference-tracked lifecycle

Orrery supports uploading files and images in issue descriptions, issue comments, and knowledge entries using the pluggable object storage layer from [ADR-0008](0008-pluggable-object-storage.md). Users can paste, drop, or pick files while drafting a new issue or knowledge entry *before* the target record exists, and teams share projects across both humans and authenticated agents.

Attachments are **project-scoped** (`attachments` rows linked to `projects.id` and `stored_objects.id`) with a permanent, authenticated URL shape (`/api/projects/:projectId/attachments/:attachmentId`) embedded directly in Markdown (`![name](url)` for inline images, `[name](url)` for downloadable files). Uploading follows the shared `stored_objects` claim-first / pending-only rule in [CODING_STANDARDS.md](../../CODING_STANDARDS.md): the `pending -> active` promotion and the `attachments` row insert commit atomically before `downloadUrl` is returned, yielding an active blob paired with an unattached `attachments` row whose `unreferenced_at` is `now()`. Saving or editing an issue, comment, or knowledge entry parses referenced attachment URLs in the same project, locks matching `attachments` rows `FOR UPDATE` (in the global order below), binds only rows whose `stored_objects.status = 'active'` (clearing `unreferenced_at` to `NULL`), and syncs reference rows transactionally, deduplicated per `(holder, attachment_id)` so pasting the same URL twice in one body never double-counts. Attachments with zero references (abandoned drafts or links removed during edits) remain downloadable for a **24-hour grace window** before a background sweep locks eligible `attachments` rows `FOR UPDATE`, re-verifies zero references and expiry, **deletes the `attachments` row**, and marks its `stored_objects` row `deleted` atomically in the same transaction—preventing both late-save races and foreign-key violations when the shared `stored_objects` orphan sweep removes the blob and metadata row. Attachments referenced by soft-deleted issues are preserved throughout the 30-day Trash window ([ADR-0006](0006-soft-delete-and-tombstone-scrubbing.md)) so restore works losslessly; when an issue is purged, its references (including those from its hard-deleted comments) are removed and any attachment with zero remaining references has its `attachments` row deleted and `stored_objects` marked `deleted` in the same transaction. Both humans and agents with project `Read` access can download attachments, and actors with `Contribute` or `Manage` access can upload them; REST and MCP responses return attachment metadata and `downloadUrl` rather than inlining binary data. To prevent tracking pixels and stored XSS, the web Markdown renderer renders inline `<img>` tags *only* for Orrery-hosted attachment URLs (keeping arbitrary external image URLs rendered as text), validates binary uploads by magic bytes, strips EXIF metadata from raster images (PNG, JPEG, WebP) while preserving animated GIFs, and serves non-image files (including SVG) strictly with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`.

Every transaction touching attachments takes locks in one global order: `projects -> issues (or the knowledge/comment holder) -> attachments` in ascending `id` order `-> stored_objects`. Saving or editing an issue, comment, or knowledge entry therefore locks and writes the holder row *before* locking matching `attachments` rows `FOR UPDATE` (ascending `id`); this matches `purgeExpiredTrash()`'s `issues -> attachments -> stored_objects` order, so a save and a purge can never AB-BA deadlock. A save binds only same-project `attachments` rows backed by an `active` `stored_objects`: an unrecognized, already-reclaimed (`deleted`/`gone`), or cross-project URL is **not bound** and is left as inert Markdown text that returns 404 if requested. Markdown text is never rejected or rewritten on save—copy-pasting old Markdown, or editing an unrelated paragraph of an issue that still contains a dead link, must not block saving—so the invariant is that every *bound* attachment reference resolves to an active, downloadable blob, not that every URL in a body resolves. `unreferenced_at` is `now()` at upload, cleared to `NULL` when bound, and reset to `now()` (starting a fresh 24-hour grace window) whenever an edit drops an attachment's reference count to zero. During the 30-day purge, `purgeExpiredTrash()` removes attachment references from both the purged issue and its hard-deleted comments in the same transaction before checking for zero remaining references.

Strict single-entity ownership (requiring an `issue_id` or `comment_id` at upload time) was rejected because it prevents pasting or dropping files on `/issues/new` and `/knowledge/new` before the record is created, and breaks copy-pasting an attachment URL across comments in the same project. Using `stored_objects`'s 15-minute `pending` TTL for draft attachments was rejected because writing a detailed issue or knowledge entry routinely takes longer than 15 minutes. Allowing arbitrary external `<img>` URLs or inline SVG rendering in Markdown was rejected to preserve Orrery's existing privacy and XSS posture.
