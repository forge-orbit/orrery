# Pluggable object storage with local filesystem default and S3-compatible backend

Orrery needs binary blob storage for user-uploaded assets—starting with Human profile photos (#160) and expanding later to issue attachments and workspace or agent icons (#159). Self-hosted deployments vary widely: small teams expect `docker compose up -d` to run just `orrery` and `postgres` with zero extra services, while larger or multi-replica deployments want an S3-compatible object store such as RustFS, MinIO, Garage, AWS S3, or Cloudflare R2.

Orrery defines a minimal, language-neutral object storage interface (`put`, `get`, `delete`, `head`) in `apps/server/src/platform/` with two adapters: a **local filesystem** default (`ORRERY_STORAGE_DRIVER=local`, storing files under `ORRERY_DATA_DIR/objects`) and an **S3-compatible** adapter (`ORRERY_STORAGE_DRIVER=s3`, supporting custom endpoints and path-style addressing for RustFS and similar servers, with RustFS offered as an optional `--profile storage` service in `compose.yaml`). Object metadata lives in a shared `stored_objects` Postgres table (`id`, `key`, `status`, `content_type`, `byte_size`, `sha256`, `created_at`, `deleted_at`, where `status` is `pending`, `active`, or `deleted`) using a backend-agnostic 1:1 relative key layout (e.g., `avatars/<humanId>/<objectId>.webp`), so operators can migrate between local disk and S3 with `rclone sync` or `aws s3 sync` and an env-var swap without rewriting database rows. Configuration lives strictly in deployment environment variables (validated at startup and checked by `/readyz`), never in runtime instance settings, to prevent split-brain storage flips. Uploads reserve a `pending` row in `stored_objects` *before* writing bytes to the storage backend, then promote that row to `active` (and mark any replaced object `deleted` with `deleted_at`) inside the committing Postgres transaction. Deletions mark `stored_objects` as `deleted` transactionally and attempt an immediate best-effort blob delete after commit; a periodic background orphan sweep removes both `deleted` objects and expired `pending` rows (e.g., older than 15 minutes) so process crashes, DB errors, or mid-upload account deactivations never leak untracked blobs. All blobs are served through authenticated Orrery endpoints enforcing workspace visibility and `X-Content-Type-Options: nosniff`, with user-uploaded images decoded, EXIF-stripped, and normalized server-side before storage.

Requiring RustFS (or another external object store) in the default Docker Compose stack was rejected to keep single-node self-hosting simple. Storing binary blobs in Postgres `BYTEA` columns was rejected because it bloats database dumps and backups once larger attachments are added. Managing storage credentials in the in-app instance settings UI (like SMTP in [ADR-0001](0001-bootstrap-and-instance-settings.md)) was rejected because switching storage backends live without a synchronized copy would strand existing blobs across two stores.
